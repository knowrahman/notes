# Module 10 — Secrets & Provider Authentication

## Where Notely is right now

```text
  notely/
  ├── modules/network, security, storage, iam, web, notely
  └── envs/dev, staging, prod        three independent state files

  Notely runs: ALB -> 2 EC2 servers -> ...nothing.

  Missing: the database.
  Lurking: a random_password sitting in state, in plaintext, since Module 3.
```

By the end of this module Notely has a real PostgreSQL database, and its password
is handled the way a production system should handle one.

Full picture: `notely-architecture.md`.

---

## Why this module exists

Two problems, and they are connected.

**Problem one: Notely has no database.** The Node.js app returns fake data. Real
notes need somewhere to live.

**Problem two: the moment you add a database, you have a password.** And Module 3
showed you exactly where passwords go:

```bash
grep -o '"result": "[^"]*"' terraform.tfstate
```

Plaintext. In a JSON file. Every time.

So this module is really about one question: **how do you build infrastructure
that needs a secret, without the secret ending up somewhere it should not be?**

---

## The core idea (one sentence)

Anything Terraform manages ends up in state in plaintext, so the goal is to
arrange for Terraform to handle the secret as briefly as possible, and for
nobody to ever type it.

> The best secret is one no human has ever seen. Generate it, store it, let the application fetch it, and never write it down.

---

## Mental model (from Node.js)

You already know this pattern.

```javascript
// Bad - the secret is in the code
const db = new Client({ password: 'hunter2' });

// Better - the secret is in the environment
const db = new Client({ password: process.env.DB_PASSWORD });

// Best - the app fetches it at runtime from a secret store
const secret = await secretsManager.getSecretValue({ SecretId: 'notely/db' });
const db = new Client({ password: JSON.parse(secret.SecretString).password });
```

Terraform has exactly the same ladder:

| Level | Terraform equivalent | Secret ends up in |
|---|---|---|
| Worst | Hardcoded in `.tf` | Git, forever |
| Bad | In a committed `.tfvars` | Git, forever |
| Okay | `TF_VAR_` from CI | State only |
| Good | Generated by Terraform, stored in Secrets Manager | State (unavoidable) |
| Best | Generated, stored, **and the app reads it at runtime** | State, but nothing else ever |

The last two rows look similar. The difference is who reads the secret: in the
"good" version, Terraform passes the password to RDS *and* the application config.
In the "best" version, Terraform only tells the application *where the secret
lives*, and the application fetches it itself with its IAM role.

## Part 1 — The AWS credential chain

Before secrets, credentials. Terraform does not have its own AWS auth — it uses
the standard chain, in this exact order:

| # | Source | Typical use |
|---|---|---|
| 1 | `provider` block arguments | **Never do this** |
| 2 | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` env vars | CI (older style) |
| 3 | `AWS_PROFILE` / `~/.aws/credentials` | Local development |
| 4 | `~/.aws/config` — SSO and assume-role profiles | Local, in an org |
| 5 | ECS container credentials | Running in a container |
| 6 | EC2 instance profile (IMDS) | Running on an EC2 build agent |

**First match wins.** So an environment variable overrides your profile, which
surprises people occasionally.

### Never put keys in a provider block

```hcl
provider "aws" {
  access_key = "AKIAIOSFODNN7EXAMPLE"      # NEVER
  secret_key = "wJalrXUtnFEMI/K7MDENG/..."  # NEVER
}
```

Committed AWS keys are scraped from public GitHub within minutes. Bots find them
automatically and spin up crypto miners. There are people whose entire job is
responding to those incidents.

### Named profiles

```bash
aws configure --profile notely-dev
export AWS_PROFILE=notely-dev
aws sts get-caller-identity     # always verify before applying
```

### Assume-role

Real organisations use one identity that assumes different roles per account:

```hcl
provider "aws" {
  region = var.region

  assume_role {
    role_arn     = "arn:aws:iam::333333333333:role/TerraformDeploy"
    session_name = "terraform-notely-prod"
  }
}
```

Or in `~/.aws/config`, which is nicer because the AWS CLI understands it too:

```ini
[profile notely-prod]
role_arn       = arn:aws:iam::333333333333:role/TerraformDeploy
source_profile = default
region         = ap-southeast-2
```

```bash
AWS_PROFILE=notely-prod terraform plan
```

### OIDC from CI — the modern answer

Long-lived access keys in a CI system are a liability: they do not expire, they
are copied into pipeline variables, and rotating them is a manual chore everyone
forgets.

**OIDC federation** replaces them. The CI system proves its identity with a
short-lived token, and AWS hands back temporary credentials.

The trust policy on the AWS side:

```hcl
data "aws_iam_policy_document" "github_actions_assume" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    # This is the important line. Without it, ANY GitHub repo
    # in the world could assume this role.
    condition {
      test     = "StringLike"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:knowrahman/notely-infra:ref:refs/heads/main"]
    }
  }
}
```

Note the `sub` condition restricts it to one repository **and one branch**. A
pull request from a fork cannot assume the role. Getting this wrong is the
classic OIDC mistake.

Module 12 wires this into a full pipeline.

> No long-lived AWS keys anywhere. Not on laptops, not in CI. Use SSO locally and OIDC in pipelines.

## Part 2 — Where secrets leak

Six places, in rough order of how often they cause incidents.

### 1. Hardcoded in `.tf` files

```hcl
resource "aws_db_instance" "notely" {
  password = "hunter2"      # committed forever
}
```

Even if you delete it later, git history keeps it. Anyone who cloned the repo has
it.

### 2. Committed `.tfvars` files

```hcl
# prod.tfvars - committed to git
db_password = "correct-horse-battery-staple"
```

Same problem, one step removed. This is why your `.gitignore` has `*.tfvars`.

### 3. The state file

Unavoidable, and the reason this module exists. Any attribute of any managed
resource is in state, in plaintext.

```bash
terraform state pull | grep -i password
```

Mitigations, not fixes:

- `encrypt = true` on the S3 backend, ideally with a customer-managed KMS key
- A restrictive bucket policy — read access to state is read access to every
  secret in it
- Never commit state

### 4. Plan files

```bash
terraform plan -out=tfplan
```

That file contains variable values, including secrets. In CI it is an artifact.
**Make it a protected artifact with a short expiry**, never a public one.

### 5. CI logs

```bash
terraform apply -var db_password=hunter2     # this appears in the log
```

Use `TF_VAR_db_password` from a masked pipeline variable instead. And mark the
variable `sensitive = true` so plan output redacts it.

### 6. `terraform output`

```bash
terraform output -json > outputs.json    # sensitive values included
```

`-json` includes sensitive values in full. Do not pipe it anywhere you would not
put the secrets themselves.

### What `sensitive = true` actually does

Worth restating precisely, because people over-trust it:

| | Protected? |
|---|---|
| Plan and apply output | **Yes** |
| `terraform output` (plain) | **Yes** |
| `terraform output -raw` | No |
| `terraform output -json` | No |
| The state file | **No** |
| A saved plan file | **No** |
| CI logs, if passed as `-var` | **No** |

It is a display filter. Useful, but not a security control.

## Part 3 — The three secret patterns

### Pattern A: Terraform generates it (recommended)

```hcl
resource "random_password" "db" {
  length  = 32
  special = true
  # RDS rejects these characters in a master password
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

resource "aws_db_instance" "notely" {
  password = random_password.db.result
}

resource "aws_secretsmanager_secret" "db" {
  name = "${var.name_prefix}/db-credentials"
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id = aws_secretsmanager_secret.db.id

  secret_string = jsonencode({
    username = aws_db_instance.notely.username
    password = random_password.db.result
    host     = aws_db_instance.notely.address
    port     = aws_db_instance.notely.port
    dbname   = aws_db_instance.notely.db_name
  })
}
```

**Why this is good:** no human ever sees or types the password. It cannot be
reused from someone's password manager. It cannot be shoulder-surfed. Rotating it
is a Terraform change.

**Why it is not perfect:** the password is in state, three times over
(`random_password`, the RDS instance, and the secret version).

### Pattern B: Ephemeral resources and write-only arguments (Terraform 1.10+)

Newer Terraform can handle values that never touch state at all.

```hcl
# An ephemeral resource - exists only during the run
ephemeral "random_password" "db" {
  length = 32
}

resource "aws_db_instance" "notely" {
  # A write-only argument - sent to the API, never stored
  password_wo         = ephemeral.random_password.db.result
  password_wo_version = 1
}
```

Bump `password_wo_version` to trigger a rotation.

This genuinely keeps the password out of state. It is the direction Terraform is
heading, but it is new enough that provider support is uneven — check the AWS
provider docs for the resource you are using.

### Pattern C: The secret already exists, Terraform reads it

```hcl
data "aws_secretsmanager_secret_version" "db" {
  secret_id = "notely/prod/db-credentials"
}

locals {
  db_password = jsondecode(data.aws_secretsmanager_secret_version.db.secret_string)["password"]
}
```

**This puts the secret in state**, because data source results are cached there.
Reading a secret is not free.

Use it when the secret is genuinely managed elsewhere — created by a security
team, rotated by a separate process.

### The best pattern: don't give Terraform the secret at all

The real answer for application configuration is that **Terraform should not pass
the secret to the application**. It should only tell the application where to find
it.

```hcl
# Terraform gives the app the secret's ARN, not its value
locals {
  user_data = templatefile("...", {
    db_secret_arn = aws_secretsmanager_secret.db.arn
    region        = var.region
  })
}

# And permission to read it
data "aws_iam_policy_document" "app" {
  statement {
    effect    = "Allow"
    actions   = ["secretsmanager:GetSecretValue"]
    resources = [aws_secretsmanager_secret.db.arn]
  }
}
```

Then the Node.js app fetches it at boot:

```javascript
const { SecretsManagerClient, GetSecretValueCommand } =
  require('@aws-sdk/client-secrets-manager');

const client = new SecretsManagerClient({ region: process.env.AWS_REGION });

async function getDbConfig() {
  const res = await client.send(new GetSecretValueCommand({
    SecretId: process.env.DB_SECRET_ARN,
  }));
  return JSON.parse(res.SecretString);
}
```

The instance's IAM role authorises the call. No password in the user-data script,
no password in an environment variable, no password on disk.

The password is still in Terraform's state — that is unavoidable when Terraform
creates the database. But it exists in exactly one place, and everything
downstream reads from Secrets Manager instead.

> Give the application the *location* of the secret and permission to read it. Never the secret itself.

## Part 4 — Secrets Manager vs SSM Parameter Store

Both store configuration. They are not interchangeable.

| | Secrets Manager | SSM Parameter Store |
|---|---|---|
| **Cost** | $0.40/secret/month + API calls | **Free** (standard tier) |
| **Automatic rotation** | Yes, built in | No |
| **Max size** | 64 KB | 4 KB standard, 8 KB advanced |
| **Encryption** | Always | Optional (`SecureString`) |
| **Cross-account** | Resource policies | Harder |
| **Versioning** | Yes | Yes |
| **Good for** | Passwords, API keys, anything rotating | Config values, feature flags, ARNs |

Practical rule: **passwords and credentials go in Secrets Manager; everything
else goes in Parameter Store**, because Parameter Store is free.

```hcl
# Free - not a secret
resource "aws_ssm_parameter" "db_host" {
  name  = "/notely/${var.environment}/db/host"
  type  = "String"
  value = aws_db_instance.notely.address
}

# $0.40/month - genuinely secret
resource "aws_secretsmanager_secret" "db" {
  name = "notely/${var.environment}/db-credentials"
}
```

### A gotcha: deletion is delayed

Secrets Manager keeps deleted secrets for 7–30 days by default, so you cannot
immediately recreate one with the same name:

```text
Error: InvalidRequestException: You can't create this secret because a secret
with this name is already scheduled for deletion.
```

For labs, set the recovery window to zero:

```hcl
resource "aws_secretsmanager_secret" "db" {
  name                    = "notely/${var.environment}/db-credentials"
  recovery_window_in_days = 0    # labs only - no undo
}
```

**Never do that in production.** The recovery window is what saves you from an
accidental delete.

## Part 5 — The `.gitignore` rules

Non-negotiable, especially in a public repository:

```text
# Terraform
**/.terraform/*
*.tfstate
*.tfstate.*
crash.log
crash.*.log
*.tfvars
*.tfvars.json
override.tf
override.tf.json
*_override.tf
*_override.tf.json
.terraformrc
terraform.rc
.terraform.tfstate.lock.info
tfplan
*.tfplan
```

Two deliberate exceptions:

**`.terraform.lock.hcl` is committed.** It is not a secret, and pinning provider
versions is the whole point.

**Share `terraform.tfvars.example`** so colleagues know what to fill in:

```bash
cp dev.tfvars dev.tfvars.example
# then remove any real values from the example
```

### If a secret does get committed

Removing the commit is **not enough**. The value is in every clone, every fork,
and possibly in GitHub's cache and in someone's CI log.

The only correct response:

1. **Rotate the secret immediately.** Assume it is compromised.
2. Then clean the history if you want to (`git filter-repo`, BFG).
3. Then work out how it happened and add a scanner.

Add `gitleaks` or `trufflehog` to your pipeline so it cannot happen twice.

Add the database, properly.

### 1. `modules/database`

**Cost: `db.t3.micro` is free tier for 12 months. Outside free tier, about

```hcl
  description = "Skip the final snapshot on destroy. True for labs, false for production."
```

`modules/database/main.tf`:

```hcl
# ---------------------------------------------------------------
# The password. Nobody types this. Nobody sees it.
# 32 characters of randomness, generated by Terraform.
#
# override_special: RDS rejects / @ " and space in master passwords,
# so we restrict the special characters to a safe set.
# ---------------------------------------------------------------
resource "random_password" "db" {
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

# RDS needs to know which subnets it may live in.
resource "aws_db_subnet_group" "this" {
  name       = "${var.name_prefix}-db"
  subnet_ids = var.subnet_ids

  tags = { Name = "${var.name_prefix}-db-subnet-group" }
}

resource "aws_db_instance" "this" {
  identifier = "${var.name_prefix}-db"

  engine         = "postgres"
  engine_version = var.engine_version
  instance_class = var.instance_class

  allocated_storage     = var.allocated_storage
  max_allocated_storage = var.allocated_storage * 2
  storage_type          = "gp3"
  storage_encrypted     = true

  db_name  = "notely"
  username = "notely_admin"
  password = random_password.db.result

  # Private subnets only, and only the app security group may connect.
  db_subnet_group_name   = aws_db_subnet_group.this.name
  vpc_security_group_ids = [var.security_group_id]
  publicly_accessible    = false

  multi_az                = var.multi_az
  backup_retention_period = var.backup_retention_days
  backup_window           = "16:00-17:00"
  maintenance_window      = "sun:17:00-sun:18:00"

  # Send Postgres logs to CloudWatch
  enabled_cloudwatch_logs_exports = ["postgresql", "upgrade"]

  deletion_protection       = var.deletion_protection
  skip_final_snapshot       = var.skip_final_snapshot
  final_snapshot_identifier = var.skip_final_snapshot ? null : "${var.name_prefix}-db-final"

  # Apply changes during the maintenance window, not immediately
  apply_immediately = false

  tags = { Name = "${var.name_prefix}-db" }

  lifecycle {
    # Uncomment in production. It makes any plan that would delete
    # this database fail, which is exactly what you want.
    # prevent_destroy = true

    ignore_changes = [
      # AWS applies minor version upgrades during the maintenance window.
      # Without this, every plan would try to revert them.
      engine_version,
    ]
  }
}

# ---------------------------------------------------------------
# Store the credentials so the application can fetch them at runtime.
# Terraform never passes the password to the app - only this ARN.
# ---------------------------------------------------------------
resource "aws_secretsmanager_secret" "db" {
  name                    = "${var.name_prefix}/db-credentials"
  description             = "Postgres credentials for ${var.name_prefix}"
  recovery_window_in_days = var.secret_recovery_days
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id = aws_secretsmanager_secret.db.id

  secret_string = jsonencode({
    username = aws_db_instance.this.username
    password = random_password.db.result
    host     = aws_db_instance.this.address
    port     = aws_db_instance.this.port
    dbname   = aws_db_instance.this.db_name
    # A ready-made connection string for the Node app
    url = "postgresql://${aws_db_instance.this.username}:${urlencode(random_password.db.result)}@${aws_db_instance.this.endpoint}/${aws_db_instance.this.db_name}"
  })
}

# Non-secret connection details go in Parameter Store, which is free.
resource "aws_ssm_parameter" "db_host" {
  name  = "/${var.name_prefix}/db/host"
  type  = "String"
  value = aws_db_instance.this.address
}

resource "aws_ssm_parameter" "db_port" {
  name  = "/${var.name_prefix}/db/port"
  type  = "String"
  value = tostring(aws_db_instance.this.port)
}
```

Note `urlencode()` on the password in the connection string. A password
containing `#` or `?` would break the URL without it. That is a real bug people
hit.

`modules/database/outputs.tf`:

```hcl
output "endpoint" {
  description = "Database endpoint, host:port"
  value       = aws_db_instance.this.endpoint
}

output "address" {
  description = "Database hostname"
  value       = aws_db_instance.this.address
}

output "secret_arn" {
  description = "ARN of the Secrets Manager secret holding the credentials. Give this to the application."
  value       = aws_secretsmanager_secret.db.arn
}

output "database_name" {
  value = aws_db_instance.this.db_name
}

# Deliberately NOT an output: the password.
# The application reads it from Secrets Manager using its IAM role.
```

That last comment matters. Resist the urge to output the password "for
convenience".

### 2. Let the app read the secret

Update `modules/iam` to add one statement:

```hcl
variable "db_secret_arn" {
  description = "ARN of the database credentials secret"
  type        = string
}

data "aws_iam_policy_document" "app_permissions" {
  statement {
    sid    = "ReadWriteAttachments"
    effect = "Allow"

    actions   = ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"]
    resources = ["${var.attachments_bucket_arn}/*"]
  }

  statement {
    sid       = "ListAttachmentsBucket"
    effect    = "Allow"
    actions   = ["s3:ListBucket"]
    resources = [var.attachments_bucket_arn]
  }

  statement {
    sid    = "WriteApplicationLogs"
    effect = "Allow"

    actions   = ["logs:CreateLogStream", "logs:PutLogEvents"]
    resources = ["${var.log_group_arn}:*"]
  }

  # NEW - and note the resource is ONE specific secret,
  # not secretsmanager:* which would let it read every secret
  # in the account.
  statement {
    sid       = "ReadDatabaseCredentials"
    effect    = "Allow"
    actions   = ["secretsmanager:GetSecretValue"]
    resources = [var.db_secret_arn]
  }
}
```

The narrow `resources` is the point. `"*"` would mean a compromised app server
could read every secret in the account.

### 3. Update the user-data template

The script gets the secret's **ARN**, never its value:

```bash
cat > /opt/notely/.env <<'ENVFILE'
NODE_ENV=${environment}
PORT=${app_port}
AWS_REGION=${region}
ATTACHMENTS_BUCKET=${attachments_bucket}
LOG_GROUP=${log_group}

```

And the Node app fetches it at boot:

```javascript
const { SecretsManagerClient, GetSecretValueCommand } =
  require('@aws-sdk/client-secrets-manager');

async function getDbUrl() {
  const client = new SecretsManagerClient({ region: process.env.AWS_REGION });
  const res = await client.send(new GetSecretValueCommand({
    SecretId: process.env.DB_SECRET_ARN,

  return JSON.parse(res.SecretString).url;
}
```

No password anywhere in the script, on disk, or in an environment variable.

## Real-World Example

A fintech team's rule: **no engineer knows any production credential.**

How they achieve it:

```text
1. Terraform generates every password with random_password
2. Every password goes straight into Secrets Manager
3. Applications read secrets at runtime using their IAM role
4. Secrets Manager rotates database passwords every 30 days via a Lambda
5. Terraform's own credentials come from OIDC - no keys exist
6. Prod state lives in a separate account; only the CI role can read it
7. Engineers get read-only prod access through SSO, with no secrets access
```

Nobody has ever typed the production database password. There is nothing to leak
in a phishing attack, nothing to accidentally paste into Slack, nothing to
offboard when someone leaves.

**The incident that got them there.** An engineer pasted a `terraform output`
into a Jira ticket to help a colleague debug. The output included a database
connection string. Jira was integrated with a Slack channel, which was archived
to a third-party search tool. The credential existed in four systems within
minutes.

Nothing was exploited. But rotating it meant a coordinated change across six
services, and the postmortem concluded the only reliable fix was making the
credential unavailable to humans in the first place.

Two Terraform-level changes came out of it: the database password stopped being
an output, and `sensitive = true` was added to everything that touched it — not
because it is a security control, but because it makes a careless paste
noticeably harder.

## Common Mistakes Beginners Make

**1. Believing `sensitive = true` protects the state file.**

It is a display filter. The state file is plaintext.

**2. Hardcoding a password to "fix it later".**

Git history is forever. Later never comes.

**3. Committing `.tfvars`.**

Check your `.gitignore` before your first commit, not after.

**4. Outputting a password "for convenience".**

Every output ends up in CI logs, screenshots and tickets eventually.

**5. `secretsmanager:GetSecretValue` on `"*"`.**

A compromised app server can now read every secret in the account. Scope it to
one ARN.

**6. Deleting the commit instead of rotating the secret.**

If it was committed, treat it as compromised. Rotate first.

**7. Putting a secret in an SSM `String` parameter instead of `SecureString`.**

`String` is not encrypted and is readable by anyone with `ssm:GetParameter`.

**8. Publishing a plan file as a public CI artifact.**

It contains variable values.

**9. Forgetting `urlencode()` on a password in a connection string.**

A `#` or `?` in the password silently breaks the URL.

**10. Leaving `recovery_window_in_days = 0` in production.**

That is the lab setting. In production the recovery window is what saves you from
a mistake.

## Hands-On Lab — Notely Gets a Database

**Cost warning.** RDS `db.t3.micro` is free tier for 12 months. Outside free
tier it is about **$0.017/hour**, roughly **$0.41 per day**. Secrets Manager is
**$0.40/month per secret**. If you also have the ALB running that is another
**$0.022/hour**.

**Total for a day with everything running: under $2.** Destroy it when you
finish.

Every part except D can be done with `terraform plan` only, at zero cost.

### Part A: Prove the leak, one more time

```bash
cd ~/terraform-labs/notely/envs/dev
terraform state pull | grep -o '"result": "[^"]*"' | head -3
```

There is the `random_password` you created in Module 3. Plaintext. This is the
problem you are about to manage.

### Part B: Build the database module

Create `modules/database/{main,variables,outputs}.tf` as shown above.

Add `versions.tf` requiring `hashicorp/aws ~> 5.0` and `hashicorp/random ~> 3.6`.

### Part C: Wire it up

- Add the `module "database"` block to `modules/notely/main.tf`
- Add `db_secret_arn` to the user-data template and the `templatefile` call

```bash
cd ~/terraform-labs/notely/envs/dev

```

Read the plan carefully. Look for:

```text
  + resource "aws_db_instance" "this" {
      + password = (sensitive value)
    }
```

`sensitive` is doing its job in the output. Now check what it did **not** do —

**If you want zero cost, stop here.** The plan shows you everything.

### Part D: Apply it (this is the billable part)

```bash
terraform apply
```

RDS takes **5–10 minutes** to create. That is normal.

```bash
terraform output
```

```text
attachments_bucket = "notely-dev-attachments-123456789012"
db_endpoint        = "notely-dev-db.abc123.ap-southeast-2.rds.amazonaws.com:5432"
db_secret_arn      = "arn:aws:secretsmanager:ap-southeast-2:123456789012:secret:notely-dev/db-credentials-AbCdEf"
url                = "http://notely-dev-alb-1234567890.ap-southeast-2.elb.amazonaws.com"
```

**Notice what is not there: the password.** There is no output for it, by design.

### Part E: Confirm the password is in state anyway

```bash
terraform state pull | python3 -c "
import json,sys
s = json.load(sys.stdin)
for r in s['resources']:
    if r['type'] == 'aws_db_instance':
        print('DB password in state:', r['instances'][0]['attributes']['password'][:8] + '...')
"
```

There it is. `sensitive = true` hid it from the terminal, and did nothing about
the state file.

**This is the lesson of the module.** The mitigations are: state is encrypted in
S3, the bucket is locked down, and nothing downstream ever sees the password —
not an output, not a script, not an environment variable.

### Part F: Retrieve it the correct way

```bash
aws secretsmanager get-secret-value \
  --secret-id $(terraform output -raw db_secret_arn) \
  --query SecretString --output text | python3 -m json.tool
```

```json
{
    "username": "notely_admin",
    "password": "xY9#mK2...",
    "host": "notely-dev-db.abc123.ap-southeast-2.rds.amazonaws.com",
    "port": 5432,
    "dbname": "notely",
    "url": "postgresql://notely_admin:xY9%23mK2...@notely-dev-db..."
}
```

Note `%23` in the URL — that is `urlencode()` handling the `#`.

That call was authorised by **your** IAM identity. The app server makes the same
call authorised by **its** instance role, which can read this secret and nothing
else.

### Part G: Prove the IAM scope is narrow

```bash
aws iam get-role-policy \
  --role-name notely-dev-app \
  --policy-name notely-dev-app \
  --query 'PolicyDocument.Statement[?Sid==`ReadDatabaseCredentials`]'
```

```json
[
    {
        "Sid": "ReadDatabaseCredentials",
        "Effect": "Allow",
        "Action": "secretsmanager:GetSecretValue",
        "Resource": "arn:aws:secretsmanager:...:secret:notely-dev/db-credentials-AbCdEf"
    }
]
```

One specific ARN. Not `*`.

### Part H: Confirm the database is unreachable

```bash
DB_HOST=$(terraform output -raw db_address)
nc -zv -w 5 $DB_HOST 5432
```

It times out. The database is in a private subnet with a security group that only
accepts connections from the app tier. From your laptop it does not exist.

That is Module 0's three-layer design working: private subnet, no internet route,
and a security group referencing another security group.

### Part I: Tear down

**Do this.** RDS and Secrets Manager are both billing.

```bash
terraform destroy
```

RDS takes several minutes to delete.

```bash
aws resourcegroupstaggingapi get-resources \
  --tag-filters Key=Project,Values=notely \
  --query 'ResourceTagMappingList[].ResourceARN' --output text

aws secretsmanager list-secrets \
  --query 'SecretList[?starts_with(Name, `notely`)].Name' --output text
```

Both should be empty. If a secret lingers, `recovery_window_in_days = 0` should
have prevented that — check the module.

### What you should have at the end

- A PostgreSQL database in a private subnet, reachable only by the app tier
- A password nobody has ever typed
- Credentials in Secrets Manager, readable by exactly one IAM role
- Proof that the password is in state regardless
- Proof that the database is unreachable from the internet

## Checkpoint — model answers

### 1. What `sensitive = true` protects

**It protects:** terminal output. Plan output, apply output, and plain
`terraform output` all show `(sensitive value)` instead of the real thing. It
also propagates — anything computed from a sensitive value becomes sensitive, so
you cannot leak it by interpolating it into a string.

**It does not protect:**

- **The state file.** Plaintext JSON, always. `terraform state pull | grep` finds
  it in seconds.
- **`terraform output -raw` and `-json`.** Both print the real value. `-json` in
  particular is often piped into files or CI variables.
- **Saved plan files.** `terraform plan -out=tfplan` embeds variable values,
  which is why a plan artifact must be protected and short-lived.

(Also: anything passed as `-var password=...` on a command line appears in CI
logs and shell history regardless of the `sensitive` flag.)

The one-line summary: it is a **display filter**, and treating it as a security
control is how secrets end up somewhere surprising.

### 2. No output for the password

Because **an output is a publication channel**, and the password does not need
one.

Outputs get printed at the end of every apply, captured in CI logs, dumped by
`terraform output -json` into files, pasted into tickets and screenshots, and
read by anything using `terraform_remote_state`. Every one of those is a place
the password would then exist.

Nothing legitimately needs it:

- **RDS** gets it directly from `random_password.db.result` inside the module
- **Secrets Manager** gets it the same way
- **The application** reads it from Secrets Manager at runtime, using its IAM role
- **A human debugging** can run `aws secretsmanager get-secret-value`, which is
  logged in CloudTrail and requires appropriate permissions

So there is no consumer, and adding an output would create exposure for
convenience alone. The real-world example in this module is exactly that failure:
a `terraform output` pasted into a ticket, which propagated to three more systems
within minutes.

The general principle: **output the location of a secret, never its value.**

### 3. Secrets Manager vs Parameter Store

| | Secrets Manager | Parameter Store |
|---|---|---|
| Cost | $0.40/secret/month + API calls | **Free** (standard tier) |
| Automatic rotation | **Yes**, built in with Lambda | No |
| Max size | 64 KB | 4 KB |
| Encryption | Always | Only with `SecureString` |
| Cross-account access | Resource policies | Harder |

**Pick Secrets Manager** for anything that is genuinely a credential and would
benefit from rotation: database passwords, API keys, private keys, OAuth client
secrets.

**Pick Parameter Store** for everything else: hostnames, ports, ARNs, feature
flags, configuration values. It is free, and at scale that matters — a hundred
secrets is $40/month, a hundred parameters is nothing.

Notely does exactly this split: the credentials JSON goes in Secrets Manager, and
`/notely/dev/db/host` and `/notely/dev/db/port` go in Parameter Store, because a
hostname is not a secret.

If you do put a secret in Parameter Store, use type `SecureString`. Plain
`String` is unencrypted and readable by anyone with `ssm:GetParameter`.

### 4. Scoping the IAM resource

Because `"*"` means **every secret in the account**, and the app server needs
exactly one.

```hcl
# Bad
actions   = ["secretsmanager:GetSecretValue"]
resources = ["*"]
```

If an attacker gets code execution on a Notely app server — through a dependency
vulnerability, an SSRF bug, anything — they inherit the instance's IAM role. With
`"*"` they can now enumerate and read every secret in the account: other
services' database passwords, third-party API keys, signing keys.

With the scoped version they get Notely's database credentials. Bad, but bounded,
and the database is still only reachable from inside the VPC.

This is least privilege, and IAM resource scoping is where it is actually
enforced. The extra effort is one line — `resources = [var.db_secret_arn]`
instead of `["*"]` — and the difference in blast radius is enormous.

The same reasoning applies to the S3 statements in the same policy: they name the
attachments bucket ARN rather than allowing `s3:*` on everything.

### 5. Deleting the commit

**No. The problem is not solved.**

Deleting a commit removes it from the branch tip, but the object remains in git's
history and, more importantly, in every place the repository has already been:

- Every clone anyone has made
- Every fork
- GitHub's own cache — a deleted commit is often still reachable by its SHA
- CI logs that checked out that commit
- Anything that mirrored or backed up the repository

Assume the value is public.

**The correct response, in order:**

1. **Rotate the secret immediately.** This is the only step that actually fixes
   anything. Change the password, revoke the key, issue a new one.
2. Then clean the history if you want to — `git filter-repo` or BFG — but treat
   this as tidying, not remediation.
3. Then work out how it happened and add a scanner (`gitleaks`, `trufflehog`) to
   the pipeline so it cannot recur.

The order matters. Teams that clean the history first and rotate later have a
window where they believe they are safe and are not.

For a **public** repository, add "audit for unauthorised use" to the list — check
CloudTrail for API calls from unfamiliar addresses.

### 6. Why `urlencode()`

Because the password is being embedded in a URL, and URLs have reserved
characters.

```text
postgresql://user:password@host:5432/dbname
```

The password sits between `:` and `@`. If it contains any character that means
something structural in a URL, the string is parsed wrongly:

| Character | What it does in a URL |
|---|---|
| `#` | Starts a fragment — everything after it is discarded |
| `?` | Starts a query string |
| `@` | Separates credentials from the host |
| `/` | Path separator |
| `:` | Separates user from password, host from port |

Notely generates passwords with `override_special = "!#$%&*()-_=+[]{}<>:?"`, which
includes `#`, `?` and `:`. So a password like `xY9#mK2` produces:

```text
postgresql://notely_admin:xY9#mK2...@host/notely
                             ^ everything from here is treated as a fragment
```

The connection silently fails with an authentication error, and you spend an hour
convinced the password is wrong.

`urlencode()` percent-escapes them — `#` becomes `%23` — and the URL parses
correctly.

This is a real bug people hit, and it is intermittent, because it only appears
when the random generator happens to pick one of those characters.

### 7. The OIDC `sub` condition

```hcl
condition {
  test     = "StringLike"
  variable = "token.actions.githubusercontent.com:sub"
  values   = ["repo:knowrahman/notely-infra:ref:refs/heads/main"]
}
```

The `sub` (subject) claim identifies **which repository and which git ref** the
token was issued to. This condition says: only a workflow running in that
repository, on that branch, may assume this role.

**Without it, any GitHub Actions workflow in the world can assume your role.**

The `aud` condition alone only proves "this token came from GitHub Actions" —
which is true of every GitHub repository on the planet. An attacker creates a
repository, adds a workflow that requests an OIDC token, and calls
`sts:AssumeRoleWithWebIdentity` against your role ARN. AWS validates the token
successfully, because it *is* a genuine GitHub token, and hands them credentials
to your account.

This is a well-documented misconfiguration and it has caused real breaches.

Two further points:

**Pin the branch, not just the repository.** `repo:owner/name:*` allows any
branch, including one created by a pull request from a fork — so an outside
contributor could obtain your production credentials by opening a PR.

**Use `StringLike` carefully.** Wildcards belong at the end of a segment, not in
the middle. `repo:knowrahman/*` would match any repository under your account,
including one you create later for an unrelated purpose.
